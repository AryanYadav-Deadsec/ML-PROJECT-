# Product Requirements Document (PRD) — v2
## CodeTrust: Explainable Detection of AI-Generated Source Code Using Code Language Models

> **v2 changelog (vs. original PRD):** adds JavaScript as a fourth supported
> language (frontend + backend, tagged not split); locks in the data-sourcing
> strategy (GitHub for human code, Anthropic API for AI code) and the
> pre-LLM cutoff date used to keep the human-written class trustworthy;
> updates tech stack, success metrics, and constraints accordingly. Sections
> unchanged from v1 are kept for completeness.

## 1. Problem Statement

There is currently no reliable, widely-available tool to determine whether
a piece of source code was written by a human or generated by an AI model.
As LLM-assisted coding becomes ubiquitous, this creates blind spots in
academic integrity checks, code review processes, hiring assessments, and
open-source contribution vetting. Existing AI-content detection research
has focused almost entirely on natural language text, leaving code — with
its distinct structural and stylistic properties — largely unaddressed.

Beyond detection itself, existing approaches (where they exist) tend to be
black boxes: a label with a confidence score, but no insight into *why* the
model made that call. CodeTrust addresses both gaps: it detects AI-generated
code *and* explains its reasoning in human-readable terms — across backend
languages (Python, Java, C++) **and** JavaScript, so both server-side logic
and frontend code can be checked.

## 2. Goals

- Build a classifier that predicts, given a source code snippet, whether it
  was human-written or AI-generated.
- Support **four languages: Python, Java, C++, and JavaScript.**
- Within JavaScript, cover both **frontend** (vanilla DOM / React) and
  **backend** (Node.js) code styles, since the two look structurally
  different enough that a model trained on only one would generalize
  poorly to the other.
- Quantify how well the detector generalizes across different LLMs (e.g.
  trained on one model's outputs, tested on another's).
- Quantify robustness against simple evasion attempts (variable renaming,
  reformatting, comment stripping).
- Produce an interpretable baseline (feature-based model) alongside two
  fine-tuned code-language transformer models — **CodeBERT** and
  **GraphCodeBERT** — trained and compared against each other and against
  the baseline.
- **Provide a human-readable explanation alongside every prediction** —
  not just a label and confidence score.

## 2.1 Supported Languages

| Language | Depth of Coverage | Notes |
|----------|--------------------|-------|
| Python | Primary — full pipeline (feature extraction, baseline, transformer) | |
| Java | Secondary — full pipeline, smaller dataset | |
| C++ | Secondary — full pipeline, smaller dataset | |
| JavaScript | Secondary — full pipeline, smaller dataset | Single `javascript` label; every sample additionally tagged `js_variant` = `vanilla` / `frontend_react` / `backend_node` for later sub-analysis. This is a metadata tag, not a separate top-level classification target — see §2.2 for why. |

Cross-language generalization (e.g. training on Python, testing on Java) is
an optional stretch goal, not a core requirement.

**Decision: JS is one label, not two.** The detector's job is human-vs-AI,
not frontend-vs-backend. Mixing both styles inside the `javascript` class
makes the model robust to both rather than overfitting to one. The
`js_variant` tag is carried on every record for free, so a frontend/backend
split can be added later as a follow-up analysis without re-collecting data.

## 2.2 Explainability Approach

Unchanged from v1. Two complementary explanation methods, one per model
type:

| Model | Explanation Method | Shows |
|-------|--------------------|-------|
| Baseline (classical ML) | SHAP or LIME on handcrafted features | Which features (naming entropy, comment density, nesting depth, etc.) drove the prediction, and in which direction |
| Transformer (CodeBERT / GraphCodeBERT) | Attention-weight visualization / token highlighting | Which tokens or code spans the model "focused on" |

Both explanation types are surfaced in the UI (see §5.1) as supporting
evidence alongside the label and confidence score.

## 3. Data Sourcing Strategy (new in v2)

This section documents the concrete data-collection decisions made for the
project, implemented in the companion `data_collection/` pipeline.

### 3.1 Human-written class — GitHub

- **Source**: GitHub public repositories, via the REST Search + Contents
  API.
- **Trustworthiness filter — cutoff date.** Both the **repository's
  creation date** and the **individual file's last commit date** must
  predate **2021-01-01**. This date is chosen to sit well before ChatGPT's
  public release (Nov 2022) and GitHub Copilot's general availability (June
  2022), minimizing the chance that a "human" sample is actually
  AI-assisted-but-unlabeled. Checking only the repo is not sufficient — an
  old repo can still have recent, possibly AI-assisted commits, so the file
  itself must independently pass the cutoff.
- **License filter.** Only permissively licensed repos (MIT, Apache-2.0,
  BSD-2/3-Clause, Unlicense) are collected, so the resulting dataset is
  redistributable for research purposes.
- **Noise filter.** Paths matching `test/`, `vendor/`, `node_modules/`,
  `build/`, `dist/`, minified/bundled JS, and lockfiles are excluded. This
  matters most for JavaScript, where build artifacts and dependency
  bundles would otherwise dominate and are not representative of authored
  code.
- **Diversity filter.** At most 2–3 files sampled per repository, so no
  single author/codebase dominates the human class.
- **Known limitation (documented for the final report):** the cutoff date
  is a heuristic, not a guarantee. Earlier-generation code-completion tools
  (e.g. TabNine, pre-2021 Copilot betas) could still have tab-completed
  fragments of a "human" file. This is a data-availability constraint
  inherited from the original PRD (§9) and is called out explicitly rather
  than glossed over.

### 3.2 AI-generated class — LLM APIs

- **Source**: a fixed seed set of programming problems (`prompts/problems.jsonl`,
  25 problems spanning arrays/strings, algorithms, data structures, and
  parsing — with 5 JS-specific prompts covering `vanilla`, `frontend_react`,
  and `backend_node` styles), sent as prompts to one or more LLMs.
- **Models used**: configurable list in `config.AI_MODELS`; each generation
  is tagged with the exact model name that produced it. This is what makes
  the cross-LLM generalization test (train on model A's outputs, test on
  model B's outputs) possible without a second data-collection pass.
- **Provider used in the reference implementation**: Anthropic's Messages
  API. Additional providers (OpenAI, etc.) can be added as long as their
  API keys and network egress are available in the runtime environment.

### 3.3 Dataset assembly

- Both classes are merged, deduplicated by content hash (protects against,
  e.g., the same GitHub file appearing via two different search pages),
  and split 70/15/15 into train/val/test, **stratified by (language ×
  label)** so no group is under-represented in any split.
- Output artifacts: `data/manifest.csv` (full labeled dataset) and
  `data/splits/{train,val,test}.jsonl`.

## 4. Non-Goals

- Not building a hardened, production-grade deployment (no auth, rate
  limiting, horizontal scaling, or monitoring) — the API/UI are for
  demonstration, not production traffic.
- Not attempting to detect *which specific* LLM generated a snippet (binary
  human/AI classification only, not multi-class attribution).
- Not covering languages beyond Python, Java, C++, and JavaScript.
- Not building a separate frontend-vs-backend classifier (see §2.1) — this
  is metadata for future work, not a v1 deliverable.
- Not building defenses against adversarial/obfuscated code specifically
  designed to fool the detector beyond basic evasion tests.
- Not handling partially AI-assisted code (e.g. human-edited AI
  suggestions) — each sample is treated as fully one class or the other.
- Not supporting user accounts, saved history, or batch/bulk uploads in the
  UI — single-file, single-request flow only.

## 5. Target Users

| User | Use Case |
|------|----------|
| Educators / academic integrity teams | Flag code submissions that may be AI-generated for manual review |
| Recruiters / technical interviewers | Sanity-check take-home coding assessments (backend *and* frontend take-homes, now that JS is covered) |
| Open-source maintainers | Flag AI-generated pull requests — including JS/React PRs — for extra scrutiny before merge |
| Researchers | Baseline/reference point for future work on code-provenance detection |

## 6. Functional Requirements

1. **Input**: Accept a source code file or snippet in Python, Java, C++, or
   JavaScript, uploaded via a web UI or sent directly to the API.
2. **Output**: Return a binary label (human / AI-generated) with a
   confidence score and a human-readable explanation.
3. **Feature extraction pipeline**: Compute AST-based and stylistic
   features from input code (nesting depth, naming entropy, comment
   density, etc.) for all four languages.
4. **Baseline model**: Classical ML model (Logistic Regression / Random
   Forest) trained on extracted features.
5. **Advanced models**: Fine-tuned code-language transformers — CodeBERT
   and GraphCodeBERT — trained and compared directly on raw code.
6. **Evaluation suite**: standard held-out metrics, cross-LLM
   generalization, evasion robustness — per language.
7. **Web UI**: upload/paste code, select or auto-detect language (incl.
   `.js`), submit, view prediction + confidence + explanation.
8. **API**: `POST /predict` — code + language in, prediction + explanation
   out.
9. **Explainability**: SHAP/LIME for the baseline, attention/token
   highlighting for the transformers.
10. **Reporting**: results, comparisons, and limitations documented in a
    final report, including the JS-specific caveats from §3.1 and §2.1.

## 6.1 Input / Output Format (API Contract)

**Endpoint:** `POST /predict`

**Request:**

```json
{
  "code": "const add = (a, b) => a + b;",
  "language": "javascript"
}
```

- `language`: one of `"python"`, `"java"`, `"cpp"`, `"javascript"`.

**Response:**

```json
{
  "label": "ai_generated",
  "confidence": 0.87,
  "language": "javascript",
  "model_used": "graphcodebert_finetuned",
  "explanation": {
    "type": "token_highlight",
    "highlights": [
      { "span": "const add = (a, b) =>", "weight": 0.42 },
      { "span": "// helper arrow function", "weight": 0.31 }
    ],
    "summary": "Flagged mainly due to generic naming and boilerplate comment style."
  }
}
```

Fields unchanged from v1 otherwise.

## 7. Success Metrics

- **Primary metric**: F1 > 0.90 for the advanced model on Python; Java,
  C++, and JavaScript targets may be lower given smaller expected dataset
  sizes.
- **Generalization metric**: accuracy drop when tested on an unseen LLM's
  outputs.
- **Robustness metric**: accuracy drop after evasion transformations
  (discussion point, not a pass/fail bar).
- **Baseline vs advanced comparison**: quantified gap between the
  handcrafted-feature baseline and each transformer, plus CodeBERT vs.
  GraphCodeBERT.
- **JS-specific check**: F1 broken out by `js_variant` (frontend vs.
  backend vs. vanilla) in the report, even though it's not a separate
  model — this tells you whether the single JS classifier is uniformly
  good or secretly only good at one style.
- **Explainability quality (qualitative)**: spot-check explanations
  against human intuition on a small manual review sample.

## 8. Deliverables

- Trained baseline model for Python, Java, C++, and JavaScript.
- Trained CodeBERT and GraphCodeBERT models for Python; other languages if
  time allows.
- Dataset (or dataset generation scripts — this is what `data_collection/`
  provides) for all four languages.
- Evaluation results: standard metrics, cross-LLM generalization, evasion
  robustness, JS-variant breakdown.
- REST API serving the trained model(s) with explanations.
- Web UI supporting all four languages.
- Final written report (`REPORT.md`), including the data-provenance and
  cutoff-date caveats as a named limitation.

## 10. Constraints

- **Time**: ~6-week course project timeline, limiting dataset size and
  model complexity — now spread across 4 languages instead of 3.
- **Compute**: likely limited to free-tier GPU resources (Colab).
- **Data availability**: verified pre-LLM human code samples are limited,
  especially for JavaScript given how fast frontend tooling/style has
  shifted; cutoff-date filtering (§3.1) narrows the usable pool further.
- **API costs**: generating AI code samples across multiple LLMs and 4
  languages multiplies the sample budget — track spend against
  `config.AI_MODELS` × `problems.jsonl` × languages.
- **GitHub rate limits**: the Search API is capped at 30 req/min even with
  a token; collecting 500 samples/language can take a while — budget time
  for this to run in the background.
- **Language scope**: full pipeline depth prioritized for Python; Java,
  C++, and JavaScript rely on smaller datasets and lighter-weight
  evaluation given time constraints.
